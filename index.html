JOIN 결과에서 동명 컬럼이 덮어써짐

증상

문제 해결 기록 3건

A

장기 일정에서 LLM 응답 JSON이 잘림

증상
14박 일정을 생성하면 JSON이 중간에서 끊기고 전체 파싱이 실패했습니다.
원인
모든 날짜와 장소를 단일 응답으로 요구해 모델의 최대 출력 토큰을 넘겼습니다.
조치
생성을 날짜별 도시 배정과 상세 일정 작성 2단계로 분리해 호출당 출력량을 줄였고, 파서에는 응답이 잘려도 마지막 완전한 일차까지 복구하는 폴백을 넣었습니다.

장기 일정에서도 생성이 실패하지 않고, 부분 손실이 나도 유효한 일정을 내놓습니다.

B

재시도가 오히려 한도 초과를 반복시킴

증상
무료 등급 호출 한도에 걸려 AI 기능이 멈췄고, 재시도해도 회복되지 않았습니다.
원인
고정 간격 재시도가 동시에 실패한 요청들을 같은 시점에 몰아넣어 429를 다시 유발했습니다.또 분당 한도 초과와 일일 할당량 소진을 같은 429로 취급해, 회복 불가능한 경우에도 최대 2분을 대기했습니다.
조치
지수 백오프에 무작위 지연을 더해 재시도 시점을 분산시키고, 두 종류의 429를 구분해 일일 할당량 소진은 즉시 중단하도록 했습니다.재시도로도 실패하면 다른 제공사 모델로 전환합니다.

회복 불가능한 오류의 불필요한 대기가 사라지고, 한도에 걸려도 기능이 멈추지 않습니다.

C

예산 재조정에서 존재하지 않는 식당을 생성

증상
예산을 줄여 달라고 하면 AI가 실제로 없는 식당을 만들어 내거나, 오히려 비용이 늘어난 결과를 돌려줬습니다.
원인
제약을 프롬프트에 적어 두는 것만으로는 모델이 지킨다고 보장할 수 없었습니다.
조치
지도 API로 반경 2km 안의 실제 저가 후보를 조회해 프롬프트에 주입하고, 응답이 그 목록에서 선택됐는지와 비용이 늘지 않았는지를 코드로 검증했습니다.검증에 실패하면 가장 적합한 후보로 자동 교체합니다.

AI 출력을 제안으로 두고 최종 결정은 코드가 내리는 구조가 되면서, 예산 재조정 결과를 신뢰할 수 있게 됐습니다.

기술 선택

Spring Boot

Spring AI가 VectorStore와 ChatClient 추상화로 RAG 파이프라인(임베딩 → 검색 → LLM 응답)을 표준화해 주고, Spring Security(OAuth2 · JWT)로 인증까지 한 생태계에서 처리할 수 있어 골랐습니다.

JSP가 아닌 React

JSP는 화면 렌더링이 서버 로직과 강하게 묶여 있어 AI 응답 대기 상태나 비동기 챗봇 인터랙션 같은 UX를 만들기 어렵습니다. React SPA + REST API로 분리해 AI 응답을 비동기로 처리하고, 프론트와 백엔드를 따로 배포·확장할 수 있게 했습니다.

pgvector가 아닌 Qdrant

회원·지출·예적금 같은 정형 데이터는 이미 MySQL로 관리하고 있어, 임베딩 유사도 검색만 담당할 벡터 전용 DB가 필요했습니다. RDB에 확장으로 얹는 대신 Qdrant를 따로 두어 정책·금융상품·고객상담 지식을 컬렉션 단위로 독립 관리하고, HNSW 인덱싱으로 검색 성능을 확보했습니다.

코딩 에이전트

문제

세 명이 각자 다른 세션에서 에이전트에 구현을 맡기다 보니, 요청 범위 밖 파일을 건드리거나 결정되지 않은 사항을 임의로 판단하는 일이 잦았습니다.

해결

디렉토리별로 역할을 나눈 규칙 문서를 두고, 코드를 생성·수정하기 전에 반드시 참조하도록 규칙을 걸었습니다.

배포

  • ALB를 단일 진입점으로 구성
  • Web · App EC2, RDS, Qdrant를 private 영역에 배치
  • SSH 접속을 제거하고 AWS SSM Session Manager 사용
  • ALB + ACM으로 HTTPS 처리 및 HTTP 리다이렉트 적용

문제 해결 기록 3건

A

2초 폴링이 참조 데이터까지 매번 다시 조회

증상
2초 간격 폴링 구간에서 N+1이 발생하고 있었습니다.관리자 화면의 API 응답속도 지표를 보고 찾아냈습니다.
